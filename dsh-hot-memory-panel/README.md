# dsh-hot-memory-panel —— 热记忆面板（只读查看 + 人工指导）

用户诉求：**看见 + 能人为指导**。所以这一页的头号判据是 **能不能一眼看出哪个会话的哪块记忆有问题**，
不是好不好看。

## 它做什么

1. 把 <DSH_HOME>/hot-memory 下每一份热记忆摊在一页上：**分区 / 每区字节 / 判定 / 前 110 字**，
   按「红 → 黄 → 绿」排序，第一条就是判据句（「N 个会话 · 黄 M · 在线 K · 磁盘 X 份 vs 本页 Y 份」）。
2. 每个会话下面可以直接写**人工指导**：**双写**到契约位置（本体读的那份）+ 面板自己的副本，并当场回读校验。

## 边界（两条硬红线）

- **只读**消费 dsh-hot-memory 的 JSON API：GET /hot-memory（列表 + 探针）、GET /hot-memory/file?id=<sessionId>（单份正文）。
  不 import 它的模块、不读它的内部状态、**不写它的任何产物**（<DSH_HOME>/hot-memory/*.md 一个字节都不碰）。
  - 现场事实：/hot-memory/file 的参数名是 **id**，不是 session（session= 会 400「缺 id」）。
- 人工指导写两处（**R24 契约**，2026-09-21 与 dsh-hot-memory v0.4.x 对上）：
  - ① 契约位置 `<DSH_HOME>/hot-memory/_guidance/<sessionId>.md` —— **本体读的就是这一份**（它只读不改、逐字保留）；
  - ② 面板副本 `<插件目录>/data/guidance/<sessionId>.md` —— 面板要能独立工作。
  两处都是「读全文 → 拼 → 原子写 → 回读校验」，只追加、不改写历史条目，目录不在就自建。
  **绝不写任何会话的热记忆文件本体**（<id>.md）：写之前有守卫拦（契约位置等于记忆目录、或与记忆文件同址，一律拒绝写）。
  任何一处没写成 → 返回 ok=false + 点名是**哪一处、什么原因**（不静默）。

## 入口

    面板：GET http://127.0.0.1:3080/hot-memory-panel
    数据：GET http://127.0.0.1:3080/hot-memory-panel?json=1       （与页面同一份数据）
    写指导：POST http://127.0.0.1:3080/hot-memory-panel/guidance   {sessionId, section, text}
    工具：hot_memory_panel（任何会话可调，只读）
    状态：data/state.json（启动时写）

## 判据（页面上的红/黄都能追到一条规则）

    E1  记忆正文为空                                  E6  蒸馏部分超预算（会被截断）
    E2  一个分区都没有                                E6b 单个分区就超预算
    E3  缺标准分区（按语料覆盖率自校准，<60% 不算）    E6c 已达预算 80%
    E4  分区标题在、内容是空的                        E6f 投喂区大小（不占预算，只作知情）
    E5  分区只有占位（- 无 / 待补充）→ 只作知情        E7  正在跑的会话记忆太久没更新
    E5b 一半以上分区是空的或只有占位（空壳记忆）        E7n 在线但空闲（不更新是正常的）→ 知情
    E8  缺「更新：」元信息行                          E7i 离线会话的老记忆（归档）→ 知情
    E9  同名分区出现多次                              E10 指导之后记忆没再更新
    E12 字节对账不平（取内容时文件被改过）            E11 指导只证明落盘、未证明被读 → 知情

三条判据是**从现场事实校准出来的**，不是拍脑袋：

- **E6 只比「蒸馏部分」**：本体 index.js:731 写着「第 6 节（中枢投喂）由代码拼装、追加在蒸馏部分之后
  （不占 maxMemoryBytes 预算）」。拿整份文件去比 2048 B 会把 4329 B / 9323 B 两份**额度正常**的记忆
  判成红（实测踩到），所以口径改成「头部 + 非投喂分区」。
- **E5 只作知情**：60 份记忆里 E5 命中 75 次，绝大多数是「未决问题：（无）」这种正常写法；
  算黄会让 44/60 个会话全变黄，把真正的 2 个超限埋掉。改成只作知情，另立 E5b 抓「空壳记忆」。
- **E7 只认「正在跑」**：本体的记忆是**每轮结束**才更新的，在线但空闲的会话不更新是正常的。

## 装 / 卸 / 改

    node install.mjs --remove   # 三样一起撤
    node verify.mjs             # 离线断言 + 现场验收（66 项，每项都印原文）

新增插件行**也是热加载**的（2026-09-21 实测：装完没重启 DSH，GET /hot-memory-panel 直接 200）。

## 接线状态（R24）：页面上显示的是**从现场解析出来的**真状态

判据链四条，每条都印在页面对应会话的「判据（现场解析）」里：

    ① 面板写的契约文件在不在、几条、几字节        ← 磁盘事实
    ② GET /hot-memory/guidance 的状态码            ← 400=挂着（缺 id 属正常）· 404=没挂载
    ③ 问本体 ?id=<sessionId> 的 exists / count     ← 本体自己的读数
    ④ 本体自报 rendered.count 与 memoFile.hasGuidanceSection  ← 有没有真渲染进记忆

状态档位（页面上每条会话一个）：

    read                绿  本体已读到 N 条，**并已渲染进记忆**（hasGuidanceSection=true）
    read-pending        灰  本体读到了，但还没渲染进记忆（等这个会话下一轮蒸馏）
    read-with-drift     黄  本体读到了，但副本里还有 M 条历史指导没进契约位置 → 本体读不到那几条
    read-partial        黄  本体读到的条数与面板写的对不上
    contract-mismatch   黄  本体说 exists=false / 解析出 0 条 → 路径或格式没对齐
    contract-written    灰  契约写好了，但本体路由还没挂载（404）
    copy-only           黄  指导只在面板副本里（写在双写之前）→ 重新下发一次即可补写
    none                灰  没下过指导

「写了 ≠ 生效了」这句话现在是**可判定的**：只有 hasGuidanceSection=true 才是绿。
另外还得记住：本体读到文件 ≠ 模型每一轮都用上了，所以绿灯的文案里也写着这条边界。

## 已知限制（诚实边界）

- 绿档（read）证明的是「本体读到了契约文件并渲染进了记忆」；**模型有没有照做**，本插件量不了。
  E10 只给一个弱信号：指导之后记忆有没有再更新过。
- 本体每次升级前，接线状态可能短暂显示「route-only / contract-mismatch」——那是契约对不上的实时提示，
  不是猜的（判据会写出本体返回的原文数值）。
- 本页的「在线/离线」来自 ctx.get('agents').list()，只有 DSH 内存里活着的会话；其余一律按离线（归档）算。
- 页面上「前 110 字」是分区开头，够判断「这块写的是什么」，但不是全文。
